### Changed — lexical search stems English suffixes and scores a stem-only match below every exact match

A query token and each document token take the same stem. Muayyad AlSadi's rule for a good stemmer: it is a hash. Relevant inflections share one hash (`stem(A) == stem(B)`). Irrelevant words keep different hashes (`stem(A) != stem(B)`). The hash does not have to be a dictionary word. A bad stemmer is one that equates two irrelevant words, or splits two relevant ones. Irregular leftovers (`built`, `indices`, `axes`) stay out of the stemmer; a synonym list is the tool for those.

The trim is Harman's s-endings plus the inflections that share a hash in code and docs: `ies` becomes `y`, `es` drops as a pair, a final `s` drops unless the word ends in `us` or `ss`, then `ly` / `ing` / `ed`, then a trailing `e` or `ie`. A doubled consonant added by `ing` or `ed` drops one letter, except `l`, `s`, `z`, and `f`. A final `ll` drops one `l` only when the stem has two or more vowels, so `cancelled` meets `canceled` and `filling` stays off `file`. `-ble` written as `-bly` drops only the `y`, so `assembly` meets `assembling`. `ply` drops the `y` only when the letter before it is a consonant other than `p`, so `simply` meets `simple` and `apply` stays off `apple`. `cookie` meets `cookies`. `copying` meets `copy`. `files` meets `file` (both `fil`). A step that would leave fewer than 3 characters is skipped.

The score is BM25 per query word, plus a capped stem part. For one word, a symbol that holds the word as typed scores the usual BM25 for that word. A symbol that holds only a stem of the word scores at most 0.5 times the weakest exact score of that word. The cap scales with the stem-only count divided by the largest stem-only count of that word. Every symbol with the typed word scores at least the weakest exact score, so a stem-only match cannot outrank an exact match of the same word. That holds for any stemmer, any file length and any pile of stem tokens, and it is why a leftover collision is acceptable. One idf covers every symbol that has either form. There is no stem document-frequency cap, so a common stem such as `split` now matches, below the exact word.

A second step handles queries with two or more words. Each query word a symbol holds as typed adds a tier bonus larger than any total the word scores can reach. A symbol with more typed words therefore ranks above one with fewer, and the capped stem scores only order symbols inside the same tier. The section and path multipliers apply to the word scores, not to the tier, so an exact match in a Markdown section still ranks above a stem-only match in code. A caller can ask for `LexMatch::All`, which returns only symbols that hold every kept query word as typed or as a stem. Every current caller keeps `LexMatch::Any`, today's any-word retrieval. The shared code is `src/stemguard.h`, and the pruned and exhaustive scoring paths use one function, so they return identical scores. The combined score stays a double until the rows are ordered. At the 1024-word query cap a float would give two symbols in the same tier one score, and symbol id would then decide the order.

Two earlier trials stayed off (`RIPWIRE_QSTEM`, `docs/EVALS.md` §7). They added the stem into the exact term's row at full weight, so a common stem such as `split` was scored with a rare term's idf and displaced hits that were already correct. The next blend damped the stem to 0.35 and dropped common stems, but nothing bounded a stem score against an exact score. In `bench/stemabc`, formulas of that kind put a related file above an exact file on 34% to 40% of 600 labelled queries. The guarded score did so on none, in OR, AND and MSM retrieval. An exact section `copying file` ranks above a section `copy file`. `file` meets `files` and stays apart from `fill`. `--for` has not been checked against a public benchmark yet. `docs/EVALS.md` lists what was and was not measured. Caches rebuild once (`kCacheVersion` 40).
